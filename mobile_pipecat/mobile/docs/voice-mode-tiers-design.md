# 음성 모드 3단계 설계 — 온디바이스 STT/TTS 모드 추가 및 오프라인 LLM 자동 전환

> 관련 문서: [openminis-analysis.md](openminis-analysis.md), native-app-tools-llm-integration-design.md
> 선행 합의: ① 현행 모드를 대체하지 않고 **모드를 추가**한다 ② OpenMinis(GPLv3)에서는 **아키텍처/패턴만 차용**하고 코드는 복사하지 않는다 ③ 인터넷 불가 시(비행기 모드 등) **온디바이스 LLM으로 자동 전환**한다 ④ 대화 컨텍스트와 메모리는 **클라이언트가 내구 저장소(정본), 서버는 세션 동안만 휘발 캐시**로 한다(§3.3~3.5)

## 1. 배경 및 목표

DuriOn의 현행 음성 대화는 WebView 내 React pipecat 클라이언트가 WebRTC로 서버 파이프라인(STT→LLM→TTS)에 연결하는 단일 모드다. 여기에 두 모드를 추가한다:

- **온디바이스 STT/TTS + 서버 LLM 모드**: 음성 처리를 기기에서 수행해 STT/TTS API 비용 제거, 원음성 비전송(프라이버시), WebRTC 미디어 경로 제거(인프라 단순화)
- **완전 오프라인 모드**: 네트워크 불가 상황(비행기 모드, 지하, 사내망 장애)에서 온디바이스 LLM으로 자동 전환해 서비스 연속성 확보

기존 모드는 최고 품질 경로로 유지한다. 네이티브 Gemini Live 동시통역 트랙은 본 설계와 무관하게 그대로 둔다.

## 2. 모드 정의

| | **Mode A: 서버 풀 파이프라인** (현행) | **Mode B: 하이브리드** (신규) | **Mode C: 오프라인** (신규) |
|---|---|---|---|
| STT | 서버 (pipecat STT 서비스) | **온디바이스** (2엔진) | **온디바이스** (시스템 엔진 전용) |
| LLM | 서버 | **서버** | **온디바이스** (소형 모델) |
| TTS | 서버 | **온디바이스** | **온디바이스** |
| 전송 | WebRTC (오디오+데이터채널) | **WebSocket + RTVI 텍스트** | 없음 |
| UI | WebView (React) | WebView 또는 네이티브 | **네이티브 Compose** |
| 턴 관리 | 서버 VAD | 1단계 PTT → 2단계 클라이언트 VAD | PTT |
| 툴 | 서버 툴 전체 + JS 플러그인 | 서버 툴 전체 + JS 플러그인 | **디바이스 로컬 툴만** |
| 품질 | 최상 (클라우드 STT/TTS) | 응답 품질 동일, 음성 자연도 하락 | 제한적 |
| 용도 | 기본, 데모, 고품질 요구 | 비용 절감, 프라이버시, 약전계 | 망 불가 시 폴백 |

### 모드 선택 정책

- 사용자가 설정에서 기본 모드(A/B)를 선택. 조직 정책으로 강제 가능(예: 프라이버시 요구 부서는 B 고정)
- **Mode C는 사용자가 선택하는 모드가 아니라 자동 폴백**이다. 네트워크 복구 시 원래 모드로 복귀

## 3. 모드 자동 전환

### 3.1 네트워크 상태 감지

- `ConnectivityManager.registerDefaultNetworkCallback` + `NET_CAPABILITY_VALIDATED`로 인터넷 유효성 감지
- 인터넷은 되지만 **DuriOn 서버만 불통**인 경우를 구분하기 위해 서버 헬스체크(경량 엔드포인트, 지수 백오프)를 병행
  - 인터넷 OK + 서버 불통 → Mode C 폴백 + "서버 연결 재시도 중" 표시 (원인 구분해 안내)
  - 인터넷 불가 → Mode C 폴백 + "오프라인 모드" 표시

### 3.2 전환 규칙 (플래핑 방지)

- **다운그레이드(→C)는 빠르게**: 진행 중 요청 실패 또는 VALIDATED 상실 후 3초 내 전환
- **업그레이드(C→A/B)는 신중하게**: VALIDATED 복구 + 서버 헬스체크 2회 연속 성공 + 최소 15초 유지 후 전환 (지하철 등에서 반복 전환 방지)
- 전환 시점은 **턴 경계**: 진행 중 발화/응답은 현재 모드에서 완결하고, 다음 턴부터 새 모드 적용. 응답 스트림 중간에 망이 끊기면 부분 응답까지 표시하고 "오프라인 모드로 전환합니다"를 TTS로 고지
- 전환은 명시적으로 고지한다(음성 + 배너). 오프라인 모드는 능력이 다르므로(툴 제한, 품질 차이) 사용자가 몰라서는 안 됨

### 3.3 데이터 상주 원칙 — 클라이언트 정본, 서버 휘발

대화 컨텍스트의 **유일한 내구 저장소는 앱**(Room, 암호화)이고, 서버는 세션 동안만 메모리에 캐시한다. 서버에 대화 DB를 두지 않는다.

```
앱 (Room, 암호화)  =  대화의 유일한 내구 저장소 (정본)
서버              =  휘발 메모리 캐시 (앱 활성 + 유휴 TTL 스코프, 디스크 기록 금지)

앱 시작:    클라이언트 → 백그라운드 프리워밍 (해시 스킵/델타 업로드, §재수화 성능 설계)
세션 시작:  서버 캐시가 이미 따뜻함 → 즉시 대화 시작 (콜드면 재수화 1회)
세션 중:    서버가 컨텍스트 누적, 변경분을 RTVI로 하행 → 클라이언트 영속
오프라인:   온디바이스 LLM이 같은 Room 저장소를 직접 읽음
복귀/재연결: 해시 일치 시 즉시 재개, 불일치 시 델타 재수화
```

- **설계 근거**: ① 서버에 보호·감사·파기 대상인 대화 DB가 사라짐(개인정보 거버넌스 단순화) ② 모드 전환·재연결·서버 재시작 복구가 전부 "재수화" 단일 메커니즘으로 통일 — 양방향 동기화 프로토콜 불필요 ③ 서버 무상태화(세션 어피니티 불필요, 수평 확장 용이)
- **보안 표현의 정확성**: 이 구조는 서버의 "저장(at-rest) 노출"을 제거하는 것이지, 처리 중 노출을 제거하는 것이 아니다. LLM 호출이 서버를 경유하는 이상 세션 중에는 내용을 처리한다. 보안 문서/고지에 이 구분을 정확히 기재할 것. 서버측 메시지 본문 로깅 금지를 코드 리뷰 체크 항목으로 강제
- **매 턴 업로드 금지**: Mode A는 서버 STT 결과로 즉시 LLM을 호출해야 하므로 턴마다 클라이언트 왕복이 끼면 안 된다. 재수화는 세션 시작/재연결 시 1회
- **재수화 성능 설계 — 프리워밍 4종 세트**: 추가 지연은 세션 시작(스냅샷 업로드 수백 ms)과 재연결 두 지점에만 생기므로 다음으로 제거한다
  1. **앱 시작 프리워밍**: 앱 실행 시 백그라운드로 컨텍스트+메모리 스냅샷을 서버 휘발 캐시에 선적재 — 사용자가 말을 시작할 때는 이미 warm
  2. **해시 스킵**: 클라이언트가 스냅샷 버전 해시를 먼저 전송, 서버에 동일 해시 캐시가 살아 있으면 업로드 생략(직전 세션 잔존 활용)
  3. **델타 업로드**: 서버가 마지막으로 아는 메시지 ID를 응답 → 그 이후 턴만 업로드. 전체 스냅샷은 최초/캐시 만료 후에만
  4. **유휴 TTL + 순단 유예**: 캐시를 세션 종료 즉시 폐기하지 않고 유휴 15~30분 TTL 유지 → 망 순단 복귀 시 해시 일치면 재수화 없이 즉시 재개. 로그아웃/앱 종료 시에는 명시적 폐기 신호 전송
  - 트레이드오프(명시): 서버 RAM 상주가 "활성 세션 동안"에서 "앱 활성 + 유휴 TTL 동안"으로 넓어진다. 사용자당 수백 KB라 용량 부담은 미미하며, 디스크 기록 금지 원칙은 동일 — 보안 고지 문구에 이 스코프를 정확히 기재할 것
- **대용량 파츠**: 이미지/큰 툴 결과는 기기에 원본을 두고 컨텍스트에는 참조만 유지, 필요 시 지연 업로드. 재수화 페이로드는 컴팩션(요약) 적용으로 상한 관리 — OpenMinis의 컨텍스트 3단 방어(캡/오프로드/컴팩션)를 클라이언트측에 적용하는 구도
- **모드 전환**: A/B→C는 온디바이스 LLM이 같은 로컬 저장소를 읽는 것으로 끝나고, C→A/B 복귀는 재수화와 동일 — 별도 역동기화 불필요
- **포기하는 것(명시)**: 다기기 로밍(사내 1인 1기기 전제로 수용), 서버측 대화 분석/품질 모니터링(필요 시 명시적 옵트인 텔레메트리로 분리)

### 3.4 메모리(mem0) — 동일 원칙 편입

메모리는 대화 이력보다 민감도가 높은 데이터(개인 사실의 누적본)이므로 같은 원칙을 적용한다. 현행 서버 PG(pgvector)+Neo4j 상주를 폐지하고 **기기 저장 + 서버 세션 스코프 처리**로 전환한다.

> 참고: "mem0 백엔드를 서버측 SQLite로 교체"는 운영 단순화일 뿐 데이터 상주 목표를 달성하지 못하므로 채택하지 않는다.

- **규모 근거**: 개인 비서 메모리는 사용자당 수백~수천 엔트리. 수천 개 × 수백 차원 벡터의 무차별 코사인 검색은 기기에서도 밀리초 단위 — pgvector 인덱싱이 필요한 규모가 아님
- **경로 A (1차 채택)** — mem0의 추출·갱신 로직(ADD/UPDATE/DELETE 판정)은 유지하고 저장만 기기로:
  ```
  세션 시작:  클라이언트가 메모리 스냅샷 업로드 (수천 엔트리 = 수백 KB 텍스트)
               → 서버가 세션 스코프 인메모리 인덱스 구성 (mem0 + FAISS in-memory)
  세션 중:    mem0 추출/판정 → 메모리 변경분(ADD/UPDATE/DELETE)을 RTVI로 하행
               → 클라이언트가 로컬 DB에 영속
  세션 종료:  서버 인덱스 폐기. 디스크 기록 없음
  ```
- **시맨틱 검색 유지**: 서버가 추출 시점에 임베딩을 계산해 레코드에 실어 하행 → 기기 SQLite BLOB 저장, 검색은 무차별 코사인. pgvector 불필요
- **경로 B (폴백)**: 세션당 인메모리 mem0 구성이 번거롭거나 갱신 로직 실효가 낮다고 판정되면, 추출은 단순 LLM 프롬프트(서버, 휘발) + 검색은 키워드×recency 스코어로 자체 경량 구현. mem0 의존성 자체를 제거
- **Neo4j(그래프 메모리)는 1차에서 제외** — 개인 비서 시나리오에서 실효가 입증될 때만 재도입
- **오프라인(Mode C)**: 온디바이스 LLM이 로컬 메모리를 직접 검색(키워드×recency, 임베딩이 있으면 코사인 병용) — 오프라인에서도 개인화 유지
- **이관**: 기존 PG 메모리를 사용자별 export → 앱 최초 실행 시 1회 임포트

### 3.5 로컬 저장소 보안

- Room/SQLite 암호화: SQLCipher 또는 Android Keystore로 감싼 키 기반 암호화. `EncryptedSharedPreferences`류는 키스토어 손상 복구 경로(alias 삭제 후 재생성)까지 설계에 포함
- 기기 분실 위협은 사내 MDM + 키스토어 암호화로 상쇄. 사용자 삭제 = 실제 삭제(서버에 잔존 사본 없음)
- 선택적 백업: 기기 로컬 내보내기(암호화 파일) 우선, 클라우드 백업은 사용자 옵트인으로만

## 4. Mode B 설계 — 온디바이스 STT/TTS + 서버 LLM

### 4.1 전송 계층

- WebRTC 불필요. **WebSocket + RTVI 텍스트 메시지**로 대체
  - 상행: 클라이언트 STT 최종 결과를 사용자 발화 텍스트로 전송
  - 하행: LLM 응답 텍스트 스트림(델타), 툴 실행 상태 이벤트(`tool_title` 포함)
- 서버는 오디오 서비스가 빠진 **텍스트 파이프라인**을 별도 태스크로 구성: 텍스트 입력 → `LLMContext` 집계 → LLM → 텍스트 출력. 기존 Mode A와 **동일한 LLM 컨텍스트/툴/시스템 프롬프트**를 공유해 모드 간 대화 품질 차이가 없게 한다
- 네이티브에서 직접 WebSocket을 쓸지, 기존 WebView 브릿지를 유지할지는 1단계에서 WebView 유지(변경 최소화), 이후 네이티브 Compose UI로 이관 검토

### 4.2 클라이언트 STT — 2엔진 전략 (OpenMinis 패턴 차용)

- **주 엔진**: `android.speech.SpeechRecognizer` — 부분 결과(라이브 자막) 지원, 무비용
- **폴백 엔진**: `AudioRecord`(PCM16/16kHz) → WAV → 서버 STT 엔드포인트 원샷 전사 — 주 엔진 품질 미달 기기/언어 대응 (Mode B에서는 서버가 있으므로 폴백이 클라우드여도 됨)
- 공통 인터페이스(`SpeechRecognitionEngine` 상당)를 정의하고 런타임 강등(주 엔진 연속 실패 시 폴백 자동 선택) 지원
- OEM 파편화 대응: 인식 서비스 존재 확인용 `<queries>` 선언, 기기별 강등 기록

### 4.3 클라이언트 TTS — 문장 단위 스트리밍 (OpenMinis 패턴 차용)

- `android.speech.tts.TextToSpeech` + `UtteranceProgressListener`
- **문장 분할기**: LLM 텍스트 스트림에서 문장 경계(`。！？.!?\n`)로 잘라 TTS 큐에 순차 공급 — 첫 문장 도착 즉시 발화 시작해 체감 지연 최소화. 숫자 사이 `.`/`,`는 경계가 아니라는 가드 필수(`3.14`, `1,000` 오분할 방지). 단위 테스트 완비할 것
- 마크다운/이모지 제거 등 발화용 텍스트 정규화 단계를 분할기 앞에 배치

### 4.4 턴 관리 — 2단계 도입

- **1단계 (PTT)**: 마이크 버튼 누름 → STT 시작 → 종료 감지(무음 또는 버튼) → 전송. barge-in 없음. TTS 재생 중 버튼을 누르면 재생 중단 후 청취(수동 barge-in)
- **2단계 (연속 대화)**: 클라이언트 VAD 도입, TTS 재생 중 사용자 발화 감지 시 재생 중단 + 서버에 interruption 통지. 에코 캔슬레이션(`VOICE_COMMUNICATION` 오디오 소스 + AEC) 실기기 검증이 선행 조건. 품질 미달 시 1단계로 확정하고 연속 대화는 Mode A 전용으로 남김

### 4.5 서버 변경 사항 (pipecat)

- 텍스트 전용 파이프라인 태스크 추가 (STT/TTS 서비스 제거, transport는 WebSocket serializer)
- 사용자 발화 텍스트를 transcription으로 주입해 기존 aggregator/턴 관리 로직 재사용
- 툴 실행 상태를 RTVI 이벤트로 하행 전송 — 이때 **`tool_title` 패턴**(모든 툴 스키마에 모델 생성 요약 필수화)을 함께 도입해 클라이언트가 "지금 뭘 하는지"를 음성 대기 중 표시

## 5. Mode C 설계 — 오프라인 온디바이스 LLM

### 5.1 LLM 런타임 선택

| 옵션 | 장점 | 단점 |
|---|---|---|
| **MediaPipe LLM Inference API** (권장 기본) | 공식 지원, GPU 위임, Gemma 3n 등 검증된 소형 모델, 라이선스 명확 | 모델 파일 배포 필요(수 GB) |
| AICore / Gemini Nano (ML Kit GenAI) | 모델 배포 불필요(OS 관리), 전력 효율 | 지원 기기 한정(최신 Pixel/Galaxy), API 제약, 한국어 품질 검증 필요 |
| llama.cpp JNI 직접 통합 | 모델 선택 자유(Qwen 등 한국어 강점 모델) | 유지보수 부담, 안정성 직접 책임 |

- **권장**: MediaPipe + Gemma 3n(E2B급, 4bit 양자화)을 기본으로 하고, AICore 지원 기기에서는 Gemini Nano를 우선 사용하는 **기회주의적 이중화**. 한국어 품질 비교 평가를 0단계 스파이크로 수행
- **기기 게이팅**: RAM 6GB 미만 또는 미지원 기기에서는 Mode C를 비활성화하고 오프라인 시 "메모/예약 명령만 가능한 제한 모드"(LLM 없이 로컬 툴 직접 실행) 또는 안내 배너만 표시
- 모델 파일은 APK에 포함하지 않고 **Wi-Fi 연결 시 사전 다운로드**(설정에서 옵트인, 저장 공간 확인). 오프라인 폴백은 모델이 이미 받아진 경우에만 활성

### 5.2 UI — 네이티브 Compose

- 오프라인에서는 WebView(React) UI를 로드할 수 없으므로 Mode C는 **네이티브 Compose 화면**이어야 한다
- 현재 디자인 프리뷰에만 연결돼 있는 `ScreenConversation` 등 Compose 대화 컴포넌트를 실제 데이터 소스(§3.3 로컬 대화 이력)에 연결해 재활용 — 미완성 자산의 활용처가 생기는 시너지
- 응답 렌더링은 단순 텍스트+최소 마크다운으로 시작. 스트리밍 렌더링이 필요해지면 OpenMinis의 적응형 스로틀(문서 길이별 파싱 주기) 패턴 참고

### 5.3 오프라인 툴셋

- 서버 툴(메일 요약, 앱 인벤토리 등)은 전부 불가. **디바이스 로컬 툴만** 소형 셋으로 노출: 알람/타이머, 연락처 검색, 앱 실행, 설정 토글, 메모
- 기존 30종 JS 플러그인은 WebView 전제라 재사용 불가 — 로컬 툴은 **네이티브 디스패처**(`device_execute(service, action, args)` 단일 진입점)로 새로 구성한다. 이 디스패처는 §4.5의 서버측 툴 통합(native-app-tools 설계)과 **동일한 서비스 카탈로그를 공유**해, 온라인 복귀 시 서버 LLM도 같은 능력을 같은 스키마로 쓰게 한다
- 소형 모델의 툴콜 신뢰도가 낮으므로: 툴 수 최소화(5개 이내), 인자 스키마 단순화, **툴 인자 JSON 3단 복구**(괄호 보정 → 타입 강제 → 필드명 퍼지 매칭) 패턴 적용

### 5.4 프롬프트/컨텍스트

- 시스템 프롬프트는 서버 것의 축약판(소형 모델 컨텍스트 예산 고려, 툴 카탈로그 축소 반영)
- 온디바이스 모델의 한계를 프롬프트와 UI 양쪽에서 고지: "오프라인 모드에서는 일부 기능이 제한됩니다"

## 7. 단계별 로드맵

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **0. 스파이크** | 온디바이스 한국어 STT/TTS 품질 실기기 평가(주력 기기 3종), 온디바이스 LLM 후보(Gemma 3n vs Gemini Nano) 한국어 툴콜 평가, **재수화·메모리 스냅샷 오버헤드 실측**(§3.3/3.4) | 품질 기준선 문서화, Mode C 기기 게이팅 기준 확정, 콜드 재수화 &lt; 500ms 확인 |
| **1. Mode B (PTT)** | 서버 텍스트 파이프라인 + WebSocket/RTVI, **로컬 이력 저장(암호화) + 재수화 프로토콜(프리워밍 4종 세트 포함, §3.3)**, 클라이언트 STT(주 엔진)/TTS + 문장 분할기, PTT UX | E2E 대화 성공, 첫 문장 발화 지연 &lt; Mode A 동등, warm 세션 시작 체감 지연 0, 서버 재시작 후 재수화 복구 |
| **2. Mode C 최소본** | Compose 대화 화면을 로컬 이력에 연결, 오프라인 LLM 통합, 자동 전환(§3.1~3.2) | 비행기 모드에서 대화 지속(같은 로컬 저장소), 복귀 시 재수화 |
| **3. 고도화** | 메모리 기기 이전(§3.4 경로 A) + PG 이관, STT 폴백 엔진, 로컬 툴 디스패처(5종), barge-in(2단계 턴 관리) 검증 | 서버 메모리 DB 폐지, barge-in 실기기 판정 → 채택 또는 Mode A 전용 확정 |

## 8. 리스크 및 미결정 사항

- **온디바이스 한국어 TTS 자연도**: 제품 첫인상 리스크. 0단계 평가 결과에 따라 Mode B 기본화 여부 결정 (기본은 A 유지, B는 옵션)
- **barge-in/AEC**: 2단계 실기기 검증 전까지 연속 대화는 Mode A 전용. 실패해도 PTT 기반 B/C는 유효
- **소형 모델 툴콜 신뢰도**: 툴 없는 순수 대화만으로 시작하는 축소 시나리오도 준비
- **모델 배포 용량**(수 GB) 사내 배포 채널 정책 확인 필요
- **모드 간 페르소나 일관성**: 서버/온디바이스 프롬프트 이원 관리 부담 — 공통 코어 + 모드별 오버레이 구조로 관리
- WebView 의존 축소(네이티브 UI 이관) 범위와 시점 — Mode B에서 WebView를 언제까지 유지할지
- **세션당 인메모리 mem0 구성 검증**(§3.4 경로 A): mem0 + FAISS in-memory의 세션당 인스턴스화가 실용적인지 0단계에서 확인. 번거로우면 경로 B로 전환
- **기기 분실 = 데이터 소실**: 컨텍스트·메모리 공통. 암호화 백업(§3.5)으로 보완하되, 백업 도입 전까지는 명시적 한계로 수용
- **기존 PG 메모리 이관**: 사용자별 export/임포트 1회성 마이그레이션 절차와 이관 완료 전 이중 운영 기간 정의 필요
